# 叶3 · 版本与兼容性

权威：Semantic Versioning 2.0、Google AIP-180/181、buf breaking、oasdiff、proto 字段号规则。

## 判据

1. **兼容性是「对既有客户端」的属性**，不是版本号大小。判定必须先问：谁在用、几个、能否升级。
   零外部客户端的内部接口可直接改（标 `n-a`），公开接口一律走加法式演进。
2. **加法 vs 破坏**：新增可选请求字段、新增响应字段、新增枚举值（对旧客户端是**读侧破坏**）、
   新增端点＝加法；改类型、改必填、删字段、改语义、改默认值、收紧校验＝破坏。
3. **「加字段也可能破坏」**：客户端严格反序列化（未知字段报错）、枚举新值落入 `default` 分支、
   响应体大小敏感（移动端）——三种情形任一成立即把加法判为破坏，须取证确认。
4. **semver 用法**：MAJOR＝破坏性、MINOR＝向后兼容新增、PATCH＝修复。0.x 期不得当作稳定契约；
   公开 API 从 0→1 是「承诺开始」而非「变更」，须在文档写明。
5. **URL/头/媒体类型版本三选一**：多机制并存＝客户端组合爆炸（blocking）。选定后写明退役策略。
6. **proto 兼容**：字段号永不复用、删除即 `reserved`、`optional` 增删影响 presence 语义、
   `int32→int64` 非二进制兼容但 JSON 兼容——须分别声明 wire 兼容与 JSON 兼容结论。
7. **ABI 兼容**：C/++ 门面关注符号导出、结构体布局、调用约定、字段增删位置（尾部追加 vs 中间插入）、
   虚表变更；任何布局变更＝重编译要求，须给 `SOVERSION` 与符号版本脚本证据。
8. **废弃（deprecation）三件套**：契约里 `deprecated: true` + 替代方案 + sunset 日期/版本；
   只写「已废弃」不给替代＝blocking。
9. **双版本并存成本**：并行维护窗口须给上限与退出条件（流量占比、客户端清单），
   无退出条件的「长期兼容」＝技术债声明。
10. **迁移可验证**：每个破坏性变更须给「旧客户端失败形态」与「检测手段」（日志/指标/契约测试）。

## 取证

`scripts/compat_probe.py --old <旧> --new <新>`（差异分级 additive/breaking/unknown）；
外部 `buf breaking` / `oasdiff` 在位时以其为准，内置结果标 `fallback`。
