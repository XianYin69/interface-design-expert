# 契约建议

## 目的

把阻塞项转成可执行的演进方案：改什么、按什么顺序改、客户端怎么跟上。

## 动作

1. 每条建议给**形状 + 理由 + 迁移路径**三段：
   - 形状：可直接粘进契约的片段（字段名、类型、状态码、消息头）。
   - 理由：引判据出处键，不得只写「最佳实践」。
   - 迁移：新旧并存窗口、废弃标记（`deprecated` + sunset 日期）、双写/双读策略。
2. 破坏性变更必须给替代方案三选一：加法式新字段 + 旧字段废弃期 / 新版本端点 + 旧版本退役期 /
   网关或适配层兜底；三者皆不可行时如实标「需停机窗口」并给时长依据。
3. proto/ABI 场景优先给 `reserved`、字段号复用禁令、`optional`/presence 语义的具体写法。
4. 事件驱动场景给投递语义（at-least-once / exactly-once 的可达性）、幂等键位置、重放与死信策略。
5. 建议之间不得互相矛盾；冲突时按 [专家判断](../专家判断/专家判断.md) 的仲裁序取舍并记录。

## 输出

`建议集`：按优先级排序，每条含形状片段、出处、迁移窗口与回滚点。

## 降级

调用方未给客户端信息 → 只给「保守方案」（加法式演进 + 废弃期），并列出需要补的信息项。
